- **`mutate_queue` 不再留半份檔案**：原本持鎖後對 `queue.json` 原地 truncate 再寫回，寫到一半被殺會留下半份 JSON，而 `queue.json` 是唯一的狀態真值。改成鎖與資料檔分離——flock 掛在獨立的 `queue.json.lock`，資料走原子替換（`replace` 會換掉 inode，鎖若掛在資料檔本身，下一個行程鎖到的是舊 inode）。狀態目錄因此多一個常駐的 `queue.json.lock`。寫入抽成 `atomic_write_json`，`mutate_queue` 與 `write_queue_new` 共用：「寫 `queue.json.tmp` → `fsync` → `os.replace` → `fsync` 父目錄」。最後一步是第二批補的——rename 改的是父目錄的目錄項，只 `fsync` 暫存檔的話斷電後可能退回舊檔；`write_queue_new` 原本連暫存檔都沒 `fsync`。保證範圍寫在該函式的 docstring：不留半份 JSON、返回前檔案與目錄項都已要求落盤；macOS 的 `fsync` 不穿透磁碟快取，不宣稱對斷電有完整持久性。
- **`ProcessLock` 改用 flock**：原本是 `O_EXCL` 建檔＋讀 pid 判斷持有者是否存活＋`unlink` 接管，三步之間有 TOCTOU，兩個 runner 可能同時認為自己接管成功。改成對鎖檔 `LOCK_EX | LOCK_NB`，互斥完全交給核心；持有者被 `SIGKILL` 時核心自動釋放，不再需要任何 pid 存活判斷。`release()` 刻意不 `unlink` 鎖檔（flock 與 unlink 併用是第二層 TOCTOU），所以 `runner.lock` 在 runner 結束後會留著，檔案存在不代表有人持有。
- **`call_claude` 逾時連孫行程一起收**：CLI 子行程原本沒有獨立 process group，逾時只 TERM／KILL 直接子行程，CLI 再衍生的行程會變孤兒，而且孤兒繼承的 stderr pipe 沒關會讓 `communicate()` 一直等下去。`Popen` 加 `start_new_session=True`，新增 `_terminate_process_group`（`os.killpg` 先 TERM、寬限期後 KILL）；逾時路徑與任何 `BaseException` 路徑都先清乾淨整個 group 才回傳或重拋。第二批修正它的兩個洞：(1) 原本用 `os.getpgid(process.pid)` 取 group id，CLI 主行程先退出、孫行程還握著 stderr pipe 時，主行程是尚未收屍的 zombie，macOS 的 `getpgid` 對它丟 `ProcessLookupError`，被解讀成「已自然結束」而改呼叫沒有 timeout 的 `communicate()`——孫行程沒收到任何訊號、runner 卡住、`runner.lock` 不放。改成直接用 `process.pid`（`start_new_session=True` `ProcessLookupError`（實測），不處理的話收尾本身會拋例外、蓋掉原本要往外傳的中斷。第四批把這個函式收斂成只有兩種結局——整個 group 確認收乾淨後正常返回，或拋例外，沒有「大概收完了」：(1) `_reap_with_limit` 等滿上限還收不完，原本是關掉 pipe、回一個帶說明文字的 tuple，呼叫端會把這一輪當成一般逾時繼續跑，而那個脫離了 group 的行程還活著、還可能在改 repo（用一個自行 `setsid` 的孫行程實測重現）。改成拋 `LeftoverProcessError`，走 crash 流程暫停並通知（鎖定時機見第五批）。(2) `PermissionError` 不再一律當成「group 已空」：新增 `_signal_group`，遇到 EPERM 先把主行程收屍、再隔一小段時間重試（`EPERM_RETRY_COUNT` 次），變成 `ProcessLookupError` 才算已空；試滿仍是 EPERM 代表 group 裡真的有送不了訊號的活行程，往外拋（第五批改成專屬的例外類別）。`call_claude` 對這兩種例外不重複收尾、原樣往外傳；中斷路徑上收尾若回報收不乾淨，該例外會取代原本的中斷（此時該讓人知道的是有殘留行程）。第五批（改用六個獨立 agent no-op，跑不到這個拓撲。第十二批的修法是記錄式——前置作業結束時把本機 HEAD 記進 queue、偵測改成「領先且本機 HEAD 不等於記錄值」——第十三批換掉：記錄只在前置作業**全部成功**時才寫，斷點回流衝突（或停止訊號、或記錄本身失敗）落在基準分支合併之後，HEAD 動了、記錄沒更新，下一輪照樣誤鎖，細節還說「不是 runner 自己做的合併」、真正的 呼叫、再推再失敗，沒有任何計數器會停，而且同原因重複暫停第二次起不通知（review 實測：第十二批之前這情況會被本機領先偵測鎖住）。推送失敗改回新結果值 `integration_push_failed`，`publish_verified_entry` 對它帶簽名 `PUSH_FAILED_SIGNATURE` 進 `enter_paused`，沿用 crash `pr_failed`。第三批修這個改動帶出來的兩個問題：(1) `pr_url` 改成只有一個寫入點（合併前的 `record_pr_result`），`finish_done_entry` 不再收 `pr_url`、也不再寫它——原本收尾無條件用這一輪的值覆寫，而 entry 分支推送失敗時這一輪的值是空的，上一輪開成功的連結會被蓋掉（用 pre-receive hook 只拒絕 entry 分支實測重現）。`pr_failed` 仍然反映這一輪的 PR 步驟有沒有出錯，通知會分清楚是「PR 未開成功」還是「既有 PR 沒有更新到這一輪的 commit」。(2) entry 不在 queue 裡時明確失敗：`import-inventory` 可以在 runner 執行中重跑，盤點檔拿掉的 entry 會從 queue 消失，而寫回用的 mutator 沿用了既有的「找不到就回 - **SIGTERM／SIGHUP 轉成例外**（複審抓到）：Python 只對 SIGINT 有內建處理，SIGTERM／SIGHUP 的預設動作是直接終止行程，任何 `except`／`finally` 都不會跑——上面 process group 的收尾與 `runner.lock` 的釋放，在 launchd 停止服務或系統登出時完全不會執行。新增 `install_shutdown_handlers` 把兩個訊號轉成 `ShutdownSignal`（繼承 `BaseException`，不會被主迴圈的 `except Exception` 當成 crash 處理），`cmd_run` 取鎖前安裝，收場路徑與 `KeyboardInterrupt` 共用。第二批把 `cmd_run` 的 `try` 往上拉到 handler 安裝之後的整段——原本必填檢查、取鎖、初始 lockfile hash 都在 `try` 外面，訊號落在那幾行會直接逃出 `main`，launchd 把正常停止當成 crash 重啟。取鎖之前收到停止訊號安靜回 `EXIT_OK`（還沒碰過任何狀態，不記事件）；取鎖之前的一般例外維持原樣往外拋、**不**走 `handle_runner_crash`——那個流程會寫 queue 與狀態目錄，而沒持鎖時可能有另一個 runner 正在跑；`finally` 只釋放真的取到的鎖。初始 lockfile hash（嚴格版，會拋例外）因此納入 crash 流程，不再是裸 traceback。第三批把「有沒有持鎖」改由 `ProcessLock.acquired` 回答（`acquire()` 在 flock 成功的當下就設定，不等診斷資訊寫完；`release()` 沒取到鎖時本來就什麼都不做），拿掉另外維護的旗標變數，handler 的安裝動作本身也移進 `try`——訊號落在「第一個 handler 已裝好、安裝函式還沒返回」的那一刻，原本一樣會逃出去。第七批（第六批送 codex 完整審，兩個 CRITICAL 同一根因，都實測重現）：把訊號轉成例外之後，例外「從當下那一行冒出來」在兩個地方會留下活的 CLI 行程、而 runner 照樣走到 `finally` 放掉 `runner.lock`——(1) `call_claude` 從 `Popen` 返回到收尾保護的 `try` 生效之間：CPython 在 CALL 返回後、變數還沒綁定前就會跑 signal handler（3.14 實測：`value = f()` 裡 `f` 返回前送訊號，例外先於綁定），例外帶著一個沒人握住的子行程離開；`Popen` 內部 fork/exec 之後的那段同理，它的 `except` 只關 fd、不殺子行程。(2) 收尾 `_terminate_process_group` 本身最長約 50 秒，期間第二次 Ctrl-C／SIGTERM 會從收尾中途跳出，group 沒 KILL 也沒確認空，`cmd_run` 當正常停止回 `EXIT_OK`。修法是「關鍵區間延後訊號」而不是 `pthread_sigmask`（mask 會被 fork 出來的 CLI 繼承，CLI 就收不到我們之後送的 SIGTERM）：handler 改成模組層的 `shutdown_signal_handler`，看到 `ShutdownDeferral` 區間深度大於 0 就只記下訊號編號、不拋；區間正常結束時才拋 `ShutdownSignal`，以例外離開（收尾回報殘留行程）則原例外優先、延後的訊號印到 stderr 後丟棄——runner 反正會走 crash 流程暫停鎖定，「停下來」的意圖已達成，用 `ShutdownSignal` 蓋過去反而把「必須鎖定」變成一次正常停止。`call_claude` 的區間從 `Popen` 開始，在收尾 `try` 裡面明確結束（延後的訊號在那裡拋、走 `BaseException` 分支收尾）；`Popen` 失敗時也明確結束（沒有子行程要收，延後的訊號直接拋，不能回一個「CLI 失敗」讓 runner 繼續跑下一個）；`with` 只當安全網，任何沒走到結束點的離開都把區間關掉，否則深度永遠不歸零、之後所有停止訊號都被無聲吃掉。`_terminate_process_group` 整段是區間。第八批把 `handle_runner_crash` 整段也納入：收尾回報殘留行程之後，凍結診斷包、把鎖定寫進 queue 的那幾秒沒有保護，第二次訊號會從 `cmd_run` 的 except handler 裡冒出來、sibling 的 except 接不到，`finally` 放鎖而鎖定沒寫，launchd 照樣重啟（實測重現）；這個區間跑完 runner 本來就以 `EXIT_PAUSED` 退出，延後的訊號印 stderr 後丟棄（`ShutdownDeferral(raise_on_normal_exit=False)`），不再拋。第十六批把 `enter_paused` 整段也納入同一種區間：不經 crash 流程的鎖定（HEAD 不符、本機領先、殘留寫入者）原本沒有保護，訊號落在「本機整合分支已退回」與「hold 寫進 queue」之間，外層當正常停止回 EXIT_OK，重啟後本機已對齊、前置作業偵測不到原本的不符，entry 放回 pending 繼續跑——宣稱必須人工確認的鎖定被整個繞過（用凍結期間觸發 handler 實測）。巢狀區間的語意也寫清楚：內層結束只減深度，訊號由最外層依它自己的離開方式決定。第九批：`end()` 不帶參數時照建構子的 `raise_on_normal_exit`（原本 `end()` 自己的預設值 True 會蓋掉建構時宣告的 False，`call_claude` 兩處顯式 `end()` 只是剛好都要 True 才沒事）；丟棄延後訊號的 stderr 訊息把「區間跑完 runner 本來就會退出」與「區間以例外結束」兩種原因分開講。SIGINT 也改由同一個 handler 接管：內建的 `KeyboardInterrupt` 不受延後，連按兩次 Ctrl-C 的第二次還是會打斷收尾；`cmd_run` 本來就把兩者當同一件事。代價：區間內第二次 Ctrl-C 沒反應，要立即中止只能 `kill -9`（會留下殘留行程）。逾時路徑的收尾在被呼叫之前就標記 `group_cleaned`——收尾完成後若拋出延後的訊號，呼叫不會「返回」，事後才標會漏掉，`BaseException` 分支就會對已空的 group 再收一次。
- **重啟後接續被中斷的等待**（第十五批，codex 抓到，1.0 起就在）：停止訊號（最常見是 launchd 停服務的 SIGTERM）落在兩種「等待」期間，重啟後都接不回去。(1) 額度等待：entry 停在 `waiting_quota`，pre-flight 只把 `running` 放回 `pending`，取件只挑 `pending`，`unblock <entry>` 只收 `failed`／`blocked`——這個 entry 永久卡住，`queue_stalled` 會通知但沒有任何指令能救、`queue.json` 依約定又不得手改。抽 `recover_interrupted_entries`（`INTERRUPTED_ENTRY_STATUSES` = running＋waiting_quota），放回是安全的：取件後、呼叫 CLI 前還有一次額度 pre-flight。(2) hard 斷點等待：斷點停在 `opened`，模組完成後的斷點檢查（`due_checkpoint`）只看 `pending` 的斷點，重啟後主迴圈直接處理下一個模組——無人看管 runner 唯一的人工閘門被繞過（用主迴圈實跑重現：git 前置在斷點等待之前就被呼叫）。主迴圈取件前先 `opened_hard_checkpoint`，有就重新 `wait_for_release`（等待逾時走既有的 `paused_for_review`），`released`／`merged` 的不再等（對照組把假的等待改成一被呼叫就拋，不然實作若真的去等、主迴圈會無限迴圈而不是紅——第一版測試就是這樣把整套測試卡了五分鐘）。
