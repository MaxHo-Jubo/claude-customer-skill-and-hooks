- **D1：舊 entry 分支重跑沒有煞車（1.0 起就在，嚴重）**。根因：entry 分支是從當時的整合分支 tip 切出的；逾時重試、blocked 後 `unblock` 重跑時分支已經存在，`prepare_branch` 只 `checkout` 它。期間別的 entry 若已合併、整合分支前進，CLI 就在舊基礎上重跑一次完整遷移，發佈段 `merge --ff-only` 必敗 → `integration_diverged` 無簽名的一般暫停 → launchd 重啟、前置作業放行、同一個 entry 放回 pending 再燒一次整個模組預算，而且同原因重複暫停不再通知——無限迴圈、沒人知道。96 個 entry 的實跑幾乎必中。附帶：`scan_secrets` 的兩點 diff 在舊分支上會把別人的變更反向算進來。修法兩層：
  - **第一層（CLI 之前）**：`prepare_branch` 對既有分支 `checkout` 後 `merge --ff --no-edit <整合分支>`（全文落 `sessions/<entry>-<n>--git-merge-integration.log`；第二批起是雙減號），成功後用 `merge-base --is-ancestor` 驗證真的跟上。失敗分兩類（`_abort_branch_catch_up`）：有衝突檔（`--diff-filter=U`，沿用前置作業的寫法）而且 `merge --abort` 成功 → 這個 entry 標 `blocked(git_state)`＋通知，主迴圈換下一個 entry；其餘（hook 拒絕、未追蹤檔會被覆寫、衝突檔清單讀不到、abort 失敗）→ runner 級 `paused(integration_dirty)`，在 CLI 之前停下、不燒預算。非衝突失敗不標 blocked 是紅隊第 3 點：那類多半是環境問題，每個 entry 都會遇到，逐一標 blocked 會把整條佇列清成 blocked。回傳值從 `(ok, detail)` 改成 `(PREPARE_READY／PREPARE_ENTRY_BLOCKED／PREPARE_PAUSE, detail)`，`cmd_run` 依此分流。
  - **第二層（發佈段）**：`merge_to_integration` 的 ff-merge 失敗改回新結果 `entry_not_ff`（切換整合分支、讀 HEAD 失敗仍是 `integration_diverged`）；`publish_verified_entry` 收到它就把 entry 標 `blocked(git_state)`、記這一輪花費、通知，回 `None` 讓主迴圈繼續，不再一般暫停。checkout／rev-parse 失敗維持暫停——重啟後前置作業在 CLI 之前就會擋下，不燒預算。
  - `module_preflight` 的「entry 分支不可能有 merge commit」註解改寫：現在會有 `prepare_branch` 合進來的那一種，它被 `--no-merges` 排除、另一個 parent 本來就在整合分支上，判定不受影響。

### 第二批：c8093cb 的 codex review（tier 3，六面向）修正

逐條查證後修正 3 個 CRITICAL（silent-failure）與相關 IMPORTANT；每條先寫會紅的測試（失敗型態皆為 AssertionError）再修。

- **ff-merge 非零不再一律當成「entry 分支不是後代」**（CRITICAL）：`merge_to_integration` 在 `merge --ff-only` 失敗後跑 `merge-base --is-ancestor <整合分支> <entry 分支>`：退出碼 1（確定不是後代）才回 `entry_not_ff`（entry 標 `blocked(git_state)`）；退出碼 0（其實可以快轉，失敗來自 `index.lock`、未追蹤檔、I/O 等環境問題）或其他非零（祖先檢查本身失敗、無法判定）回 `integration_diverged`，runner 級暫停、detail 寫明是哪一種。第一批的寫法會把環境問題標成永久 blocked，環境恢復後也不會自動重試，同一個環境問題還會把後面的 entry 逐一清成 blocked。
- **兩條新 blocked 路徑的「寫 blocked＋通知」納入同一個 `ShutdownDeferral` 區間**（CRITICAL）：`_abort_branch_catch_up` 的合併衝突與 `publish_verified_entry` 的 ff 失敗（後者連 `refresh_bundle_snapshot` 一起）。停止訊號落在兩步之間時，第一批會留下「entry 已 blocked、重啟後不再取件，但通知永遠不會送出」。用預設的 `raise_on_normal_exit=True`：區間結束後延後的訊號照樣拋出、runner 照常停止——不同於 `enter_paused`／`handle_runner_crash`（那兩處跑完本來就要退出，所以丟棄）。`ShutdownDeferral` 的類別 docstring 補上第 (5) 類使用點。既有的 CLI blocked（`apply_outcome`）與 L1 沒過兩條 blocked 路徑有同樣的窗，1.1.1 起就在，這批不動（見下方「不在這批」）。
- **`mark_entry_blocked` 找不到 entry 改成拋 `RuntimeError`（訊息帶 entry id）**（CRITICAL）：第一批安靜回 `None`，而四個呼叫端都忽略回傳值、照樣通知「已 blocked」並繼續。例外在 mutator 內拋出，queue 不寫入；四個呼叫端都在 `cmd_run` 的 `try` 內，一律走 crash 流程暫停，與 `record_pr_result`、`finish_done_entry` 對「entry 已不在 queue」的處理一致。
- **子行程 log 檔名改成 `<entry>-<n>--<name>.log`（雙減號）**：單減號時 `orders-sub-1-a-sub-5-npm-ci.log` 也符合 `orders-sub` 第 1 次的 log，錨定比對仍有歧義（診斷包混入別的 entry 的 log、取號無故跳號）。`session_index.ATTEMPT_FILE_PATTERN` 的 log 分支改成 `--<小寫開頭、不含 -- 的名稱>.log`，新增常數 `LOG_SEPARATOR`；`.json`／`.stream.jsonl`／`.claim` 不變，runner 級的 `runner-<時間>-<name>.log` 不變。舊格式的 log 留在原處，但不再被歸到任何 entry（不進診斷包、不參與取號）。
- **合併失敗收尾抽成共用 helper `abort_failed_merge`**（＋`merge_cleanup_notes` 組附註）：讀衝突檔清單 → `merge --abort`，回傳（衝突檔／清單讀取錯誤／abort 錯誤），不分類。三個呼叫點：`module_preflight` 的基準分支合併與斷點回流、`_abort_branch_catch_up`。前置作業那兩處原本忽略清單讀取失敗與 abort 失敗，現在寫進 detail，暫停原因（`master_conflict`）與流程不變。`_abort_branch_catch_up` 的暫停 detail 不再一律寫「非衝突」：清單讀不到寫 `無法判定是否衝突`、有衝突但 abort 失敗寫 `有衝突但 abort 失敗` 並列出衝突檔。

- **`ProcessLock` 改用 flock**：原本是 `O_EXCL` 建檔＋讀 pid 判斷持有者是否存活＋`unlink` 接管，三步之間有 TOCTOU，兩個 runner 可能同時認為自己接管成功。改成對鎖檔 `LOCK_EX | LOCK_NB`，互斥完全交給核心；持有者被 `SIGKILL` 時核心自動釋放，不再需要任何 pid 存活判斷。`release()` 刻意不 `unlink` 鎖檔（flock 與 unlink 併用是第二層 TOCTOU），所以 `runner.lock` 在 runner 結束後會留著，檔案存在不代表有人持有。
- **`call_claude` 逾時連孫行程一起收**：CLI 子行程原本沒有獨立 process group，逾時只 TERM／KILL 直接子行程，CLI 再衍生的行程會變孤兒，而且孤兒繼承的 stderr pipe 沒關會讓 `communicate()` 一直等下去。`Popen` 加 `start_new_session=True`，新增 `_terminate_process_group`（`os.killpg` 先 TERM、寬限期後 KILL）；逾時路徑與任何 `BaseException` 路徑都先清乾淨整個 group 才回傳或重拋。第二批修正它的兩個洞：(1) 原本用 `os.getpgid(process.pid)` 取 group id，CLI 主行程先退出、孫行程還握著 stderr pipe 時，主行程是尚未收屍的 zombie，macOS 的 `getpgid` 對它丟 `ProcessLookupError`，被解讀成「已自然結束」而改呼叫沒有 timeout 的 `communicate()`——孫行程沒收到任何訊號、runner 卡住、`runner.lock` 不放。改成直接用 `process.pid`（`start_new_session=True` `ProcessLookupError`（實測），不處理的話收尾本身會拋例外、蓋掉原本要往外傳的中斷。第四批把這個函式收斂成只有兩種結局——整個 group 確認收乾淨後正常返回，或拋例外，沒有「大概收完了」：(1) `_reap_with_limit` 等滿上限還收不完，原本是關掉 pipe、回一個帶說明文字的 tuple，呼叫端會把這一輪當成一般逾時繼續跑，而那個脫離了 group 的行程還活著、還可能在改 repo（用一個自行 `setsid` 的孫行程實測重現）。改成拋 `LeftoverProcessError`，走 crash 流程暫停並通知（鎖定時機見第五批）。(2) `PermissionError` 不再一律當成「group 已空」：新增 `_signal_group`，遇到 EPERM 先把主行程收屍、再隔一小段時間重試（`EPERM_RETRY_COUNT` 次），變成 `ProcessLookupError` 才算已空；試滿仍是 EPERM 代表 group 裡真的有送不了訊號的活行程，往外拋（第五批改成專屬的例外類別）。`call_claude` 對這兩種例外不重複收尾、原樣往外傳；中斷路徑上收尾若回報收不乾淨，該例外會取代原本的中斷（此時該讓人知道的是有殘留行程）。第五批（改用六個獨立 agent 審第四批，抓到第四批自己沒做到的兩件事，都實測或逐行查證屬實）：(3) 「確認收乾淨」原本的證據只有「pipe 關閉」——TERM 之後主行程一死、pipe 一關，`communicate` 零秒返回，函式就正常返回了，而同一個 group 內忽略 SIGTERM、又沒握 pipe 的行程還活著，SIGKILL 永遠不會送（實測重現；這個洞從第二批就在）。現在正常返回要兩個條件都成立：pipe stderr、通知照樣說「已鎖定（hold）」——磁碟滿或 I/O 錯誤時鎖定只存在記憶體裡，launchd 幾分鐘後照常重啟。現在通知改說「鎖定沒有寫進狀態檔，請立即 `launchctl unload`」，事件紀錄帶 `hold_persisted`；沒有鎖定的暫停落盤失敗也加一行說明。(7) plist 範本補 `ExitTimeOut`（90 秒）：`launchctl unload`／`stop` 送 SIGTERM 之後，runner 收乾淨 process group 最壞要約 50 秒（TERM 寬限 30＋有上限收屍 10＋KILL 後確認 10）再凍結診斷包、寫入鎖定，而 `man launchd.plist` 只說預設值 system-defined——不寫的話 runner 可能在鎖定落盤之前就被 SIGKILL。測試釘住 `ExitTimeOut` 必須大於三個常數的總和，改 `TERM_GRACE_SECONDS`／`REAP_LIMIT_SECONDS` 會一起紅。

runner 自己，而且同原因不再通知。推送失敗時先 `ls-remote` 問遠端，已經是預期的 commit 就照 done 收尾（用「真的推、然後回報失敗」的假 git 實測）。第十四批：`ls-remote` 本身失敗不再當成「遠端沒收到」——那時什麼都不能斷定，退回等於遠端若收到了本機就落後、說可重試等於再燒一次模組；回 `integration_unrecovered` 讓呼叫端鎖定，本機留在合併後的 commit 當證據，細節寫明兩種人工判定各自要跑什麼。三處訊息說實話：合併後讀不到 HEAD 與「HEAD 在檢查期間又變了」分開講（人會去追不存在的寫入者）、未追蹤檔清單讀取失敗不再與「沒有未追蹤檔」同形、本機 tip 讀不到不再渲染成空字串。`finish_done_entry` 把 `integration_tip_sha` 與 entry 的 done 併成同一次 `mutate_queue`（原本分兩次寫，中間一斷就是 tip 已前進、entry 還是 `running`）。PR 一開成功就把 `pr_url` 寫進 queue，`push_branch_and_open_pr` 看到 entry 已有 `pr_url` 時只推分支、不再 `gh pr create`——原本連結只留在暫停訊息裡，重跑會重開、失敗、再把真的存在的 PR 記成 `pr_failed`。第三批修這個改動帶出來的兩個問題：(1) `pr_url` 改成只有一個寫入點（合併前的 `record_pr_result`），`finish_done_entry` 不再收 `pr_url`、也不再寫它——原本收尾無條件用這一輪的值覆寫，而 entry 分支推送失敗時這一輪的值是空的，上一輪開成功的連結會被蓋掉（用 pre-receive hook 只拒絕 entry 分支實測重現）。`pr_failed` 仍然反映這一輪的 PR 步驟有沒有出錯，通知會分清楚是「PR 未開成功」還是「既有 PR 沒有更新到這一輪的 commit」。(2) entry 不在 queue 裡時明確失敗：`import-inventory` 可以在 runner 執行中重跑，盤點檔拿掉的 entry 會從 queue 消失，而寫回用的 mutator 沿用了既有的「找不到就回 `None`」寫法，等於寫不進去還照樣合併推送。`record_pr_result` 每一輪都會跑（不論有沒有拿到連結），找不到 entry 就拋例外——這時整合分支還沒動；合併推送的那幾秒內才消失的，`finish_done_entry` 照樣記下 tip（遠端確實已前進），然後拋例外，不假裝這個 entry 完成了。
- **`git_out_or_raise`**：`git_out` 對任何失敗一律回空字串，「指令失敗」與「合法的空結果」分不出來。新增嚴格版，只用在會拿結果推導結論的呼叫點（`l1_verify` 判斷有沒有 commit、`collect_closing_data` 讀 entry commit；第十四批起 `checkpoint_refs` 列本機 ref 也用它——失敗不可與「沒有斷點分支」混淆）；其餘呼叫點維持寬容版不動，不擴大改動範圍。
- **`file_sha1` 分嚴格與寬容兩版**：原本「檔案不存在」「權限錯誤」「I/O 錯誤」全部回 `None`。`file_sha1` 改成只有不存在回 `None`、其餘讀取失敗拋例外；新增 `file_sha1_or_none` 給純診斷用途（環境指紋的兩個 sha1）。`lockfile_hash` 與 `record_r15_hashes` 用嚴格版；`changed_r15_files` 對單一檔案讀取失敗明確視為「已變動」而不中斷整份報表。後兩者是複審抓到的二次修正——第一版兩邊都用寬容版，同一檔兩次都讀不到會變成 `None == None`，被判成「沒變動」。
- **`gh pr create` 退出碼 0 但沒有 URL 視為失敗**：`push_branch_and_open_pr` 原本會回傳空字串當 PR 連結，下游記成 `pr_failed: false` 卻沒有真的 PR。找不到合法 URL 一律回 `(None, 錯誤訊息)`。第四批把「合法」從「以 http 開頭」收緊成 PR 連結的形狀（`PR_URL_RE`：`http(s)://<host>/…/pull/<編號>`，整行比對），抽成 `extract_pr_url`，頁面 PR 與斷點 PR 共用——`pr_url` 現在會立刻寫進 queue、而且有值就不再開 PR，把 `gh` 成功退出時印的登入／更新提示網址記進去，這個 entry 就永遠不會有 PR。同一批也補上：PR 步驟與合併都失敗時，暫停原因與事件紀錄裡兩個錯誤都留下來（原本收尾不會執行，PR 的錯誤不出現在任何地方）。第五批把 `open_checkpoint` 也改成同一個標準（空連結就 `mark_checkpoint_failed`、回 `False`），第六批**還原**：四個審查面向都只看了 `open_checkpoint` 本身、沒看兩個呼叫端，我照做也沒看。`handle_checkpoints` 只在它回 `True` 時暫停 hard 斷點——回 `False` 等於人工閘門消失，runner 一路把後面的 wave 合進整合分支；auto 斷點在開成功之前不在 queue 裡，`mark_checkpoint_failed` 是空轉，entry 沒蓋章的話 `auto_checkpoint_needed` 永遠不歸零，每完成一個模組就再推一支 `cp-auto-*` 分支、再開一個真的 draft PR、再發一則通知，沒有上限（用本版的測試 fixture 實跑重現）。斷點 PR 現在拿到空連結照樣寫 `opened`、蓋章、回 `True`，通知寫「gh 未回傳連結，請到 GitHub 確認分支 … 是否已有 PR」並附 gh 的輸出；`checkpoint_opened` 事件的 `pr` 欄位是空字串。兩個呼叫端的行為各釘一個測試（hard 仍暫停、auto 只開一次）。正解是查該分支既有的 PR 沿用、查不到才失敗並把失敗落盤——那是下面已知缺口 (c)，併入 1.1.2。頁面 PR 的「空連結就是失敗」不變。第五批另外把 PR 的錯誤改在凍結診斷包**之前**記下，操作者帶走的那個包裡才有；這一點保留。`open_checkpoint` 其餘兩條失敗路徑（cp 分支推不上去、`gh` 非零退出）的訊息補上 cp 分支名——後者發生時分支已經在 origin 上，人工接手要知道對哪支開 PR。
- **SIGTERM／SIGHUP 轉成例外**（複審抓到）：Python 只對 SIGINT 有內建處理，SIGTERM／SIGHUP 的預設動作是直接終止行程，任何 `except`／`finally` 都不會跑——上面 process group 的收尾與 `runner.lock` 的釋放，在 launchd 停止服務或系統登出時完全不會執行。新增 `install_shutdown_handlers` 把兩個訊號轉成 `ShutdownSignal`（繼承 `BaseException`，不會被主迴圈的 `except Exception` 當成 crash 處理），`cmd_run` 取鎖前安裝，收場路徑與 `KeyboardInterrupt` 共用。第二批把 `cmd_run` 的 `try` 往上拉到 handler 安裝之後的整段——原本必填檢查、取鎖、初始 lockfile hash 都在 `try` 外面，訊號落在那幾行會直接逃出 `main`，launchd 把正常停止當成 crash 重啟。取鎖之前收到停止訊號安靜回 `EXIT_OK`（還沒碰過任何狀態，不記事件）；取鎖之前的一般例外維持原樣往外拋、**不**走 `handle_runner_crash`——那個流程會寫 queue 與狀態目錄，而沒持鎖時可能有另一個 runner 正在跑；`finally` 只釋放真的取到的鎖。初始 lockfile hash（嚴格版，會拋例外）因此納入 crash 流程，不再是裸 traceback。第三批把「有沒有持鎖」改由 `ProcessLock.acquired` 回答（`acquire()` 在 flock 成功的當下就設定，不等診斷資訊寫完；`release()` 沒取到鎖時本來就什麼都不做），拿掉另外維護的旗標變數，handler 的安裝動作本身也移進 `try`——訊號落在「第一個 handler 已裝好、安裝函式還沒返回」的那一刻，原本一樣會逃出去。第七批（第六批送 codex 完整審，兩個 CRITICAL 同一根因，都實測重現）：把訊號轉成例外之後，例外「從當下那一行冒出來」在兩個地方會留下活的 CLI 行程、而 runner 照樣走到 `finally` 放掉 `runner.lock`——(1) `call_claude` 從 `Popen` 返回到收尾保護的 `try` 生效之間：CPython 在 CALL 返回後、變數還沒綁定前就會跑 signal handler（3.14 實測：`value = f()` 裡 `f` 返回前送訊號，例外先於綁定），例外帶著一個沒人握住的子行程離開；`Popen` 內部 fork/exec 之後的那段同理，它的 `except` 只關 fd、不殺子行程。(2) 收尾 `_terminate_process_group` 本身最長約 50 秒，期間第二次 Ctrl-C／SIGTERM 會從收尾中途跳出，group 沒 KILL 也沒確認空，`cmd_run` 當正常停止回 `EXIT_OK`。修法是「關鍵區間延後訊號」而不是 `pthread_sigmask`（mask 會被 fork 出來的 CLI 繼承，CLI 就收不到我們之後送的 SIGTERM）：handler 改成模組層的 `shutdown_signal_handler`，看到 `ShutdownDeferral` 區間深度大於 0 就只記下訊號編號、不拋；區間正常結束時才拋 `ShutdownSignal`，以例外離開（收尾回報殘留行程）則原例外優先、延後的訊號印到 stderr 後丟棄——runner 反正會走 crash 流程暫停鎖定，「停下來」的意圖已達成，用 `ShutdownSignal` 蓋過去反而把「必須鎖定」變成一次正常停止。`call_claude` 的區間從 `Popen` 開始，在收尾 `try` 裡面明確結束（延後的訊號在那裡拋、走 `BaseException` 分支收尾）；`Popen` 失敗時也明確結束（沒有子行程要收，延後的訊號直接拋，不能回一個「CLI 失敗」讓 runner 繼續跑下一個）；`with` 只當安全網，任何沒走到結束點的離開都把區間關掉，否則深度永遠不歸零、之後所有停止訊號都被無聲吃掉。`_terminate_process_group` 整段是區間。第八批把 `handle_runner_crash` 整段也納入：收尾回報殘留行程之後，凍結診斷包、把鎖定寫進 queue 的那幾秒沒有保護，第二次訊號會從 `cmd_run` 的 except handler 裡冒出來、sibling 的 except 接不到，`finally` 放鎖而鎖定沒寫，launchd 照樣重啟（實測重現）；這個區間跑完 runner 本來就以 `EXIT_PAUSED` 退出，延後的訊號印 stderr 後丟棄（`ShutdownDeferral(raise_on_normal_exit=False)`），不再拋。第十六批把 `enter_paused` 整段也納入同一種區間：不經 crash 流程的鎖定（HEAD 不符、本機領先、殘留寫入者）原本沒有保護，訊號落在「本機整合分支已退回」與「hold 寫進 queue」之間，外層當正常停止回 EXIT_OK，重啟後本機已對齊、前置作業偵測不到原本的不符，entry 放回 pending 繼續跑——宣稱必須人工確認的鎖定被整個繞過（用凍結期間觸發 handler 實測）。巢狀區間的語意也寫清楚：內層結束只減深度，訊號由最外層依它自己的離開方式決定。第九批：`end()` 不帶參數時照建構子的 `raise_on_normal_exit`（原本 `end()` 自己的預設值 True 會蓋掉建構時宣告的 False，`call_claude` 兩處顯式 `end()` 只是剛好都要 True 才沒事）；丟棄延後訊號的 stderr 訊息把「區間跑完 runner 本來就會退出」與「區間以例外結束」兩種原因分開講。SIGINT 也改由同一個 handler 接管：內建的 `KeyboardInterrupt` 不受延後，連按兩次 Ctrl-C 的第二次還是會打斷收尾；`cmd_run` 本來就把兩者當同一件事。代價：區間內第二次 Ctrl-C 沒反應，要立即中止只能 `kill -9`（會留下殘留行程）。逾時路徑的收尾在被呼叫之前就標記 `group_cleaned`——收尾完成後若拋出延後的訊號，呼叫不會「返回」，事後才標會漏掉，`BaseException` 分支就會對已空的 group 再收一次。
- **重啟後接續被中斷的等待**（第十五批，codex 抓到，1.0 起就在）：停止訊號（最常見是 launchd 停服務的 SIGTERM）落在兩種「等待」期間，重啟後都接不回去。(1) 額度等待：entry 停在 `waiting_quota`，pre-flight 只把 `running` 放回 `pending`，取件只挑 `pending`，`unblock <entry>` 只收 `failed`／`blocked`——這個 entry 永久卡住，`queue_stalled` 會通知但沒有任何指令能救、`queue.json` 依約定又不得手改。抽 `recover_interrupted_entries`（`INTERRUPTED_ENTRY_STATUSES` = running＋waiting_quota），放回是安全的：取件後、呼叫 CLI 前還有一次額度 pre-flight。(2) hard 斷點等待：斷點停在 `opened`，模組完成後的斷點檢查（`due_checkpoint`）只看 `pending` 的斷點，重啟後主迴圈直接處理下一個模組——無人看管 runner 唯一的人工閘門被繞過（用主迴圈實跑重現：git 前置在斷點等待之前就被呼叫）。主迴圈取件前先 `opened_hard_checkpoint`，有就重新 `wait_for_release`（等待逾時走既有的 `paused_for_review`），`released`／`merged` 的不再等（對照組把假的等待改成一被呼叫就拋，不然實作若真的去等、主迴圈會無限迴圈而不是紅——第一版測試就是這樣把整套測試卡了五分鐘）。
- **通知的長度上限以字元計，鎖定的指示放最前面且放得下**（第十二、十三批，review 實測）：`helpers/notify.sh` 的 `max_text_chars=300` 靠 `${#text}` 與 `${text:0:N}`，bash 3.2 在 locale 不是 UTF-8 時（沒設、或 `C`／`POSIX`）是 byte 語意——300 對中文只剩約 100 個字，還可能斷在半個 UTF-8 字元中間。第十二批把它寫成「launchd 環境沒有 `LANG`，細節一個字都送不到」，第十三批的 review 查證這說過頭：runner 用 CPython 啟動這支腳本，PEP 538 已經把 `LC_CTYPE=C.UTF-8` 帶給子行程（實測 `env -i python3 → bash` 得到字元數），runner 那條路徑本來就是字元語意；byte 語意只發生在手動執行或別的呼叫端。守衛保留當防禦：有效的 locale（照 `LC_ALL` > `LC_CTYPE` > `LANG` 的優先序取第一個有設定的）不含 UTF-8 時補 `LC_ALL=C.UTF-8`（第十二批只擋「三個全空」、`LANG=C` 照樣 byte；第十三批改成三個串起來找 UTF-8，`LC_ALL=C` 配 `LANG=en_US.UTF-8` 會因為 LANG 含 UTF-8 而放過、有效值其實是 C——第十六批 codex 抓到；用 `LC_ALL` 是因為 `LC_ALL=C` 會蓋過 `LC_CTYPE`），已是 UTF-8 的一律尊重；第十七批再改成不看名字、直接量：一個中文字 `${#…}` 算出來不是 1 才補 `LC_ALL=C.UTF-8`——名字寫 UTF-8 不代表這台有那個 locale（glibc 寫法 `en_US.utf8` 在 macOS 沒有，bash 安靜退回 C，實測 30 bytes），優先序也不必自己算；測試在 `env -i`、`LANG=C`、`LC_ALL=C LANG=en_US.UTF-8`、`LANG=en_US.utf8` 四種下只 source 到 locale 段結尾、驗 10 個中文字的長度是 10。真正的瓶頸是預算：300 字扣掉標題（約 38）、`診斷:` 一行（約 63）、鎖定前綴（約 75）只剩約 124 字給細節，第十二批的本機領先動作句用正式預設分支名組出來 191 字（分支名重複五次），`git reset --hard` 與「再 `unblock --runner`」全被切掉、人只看到前綴寫死的 `unblock --runner`（第十二輪實測）。第十三批壓成一句「先看下列 commit、確認保留後 git checkout X && git reset --hard origin/X，再 unblock --runner。」（分支名兩次），抽成 `local_ahead_detail`；第十三批的測試拿實作自己的 `LOCAL_AHEAD_ACTION_MAX_CHARS` 當期望值（codex 指出常數改成 1000 測試照樣綠），第十六批改成用預設分支名走一次真的 `enter_paused`、照 notify.sh 的規則組字並以 300 字這個外部契約截斷、斷言截斷後仍看得到 `reset --hard` 與 `unblock --runner`；退不回去那種的動作句 51 字，本來就放得下。兩種鎖定的細節都是「動作在前、診斷在後」。退不回去那種第十六輪實測全文 684 字，300 字截在兩個 40 字元 sha 的不符敘述裡，「合併前的 sha」（人工退回唯一的依據）與退不回去的原因全在截斷線之外——第十七批把退不回去的說明（開頭就是合併前 sha，縮成 12 字元）排在不符敘述之前、鎖定前綴縮短、publish 的動作句縮短，並加一個走真的 `publish_verified_entry`＋300 字截斷的測試釘住 sha、原因、兩個 unblock 都看得到；`--keep` 中止的訊息改取 git
